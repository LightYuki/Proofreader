# 开源建设规划

评估日期：2026-10-01。目标仓库：<https://github.com/LightYuki/Proofreader>。应用继续使用 Proofread 名称与 `com.proofread.desktop` 配置标识，初始版本保持 1.0.0。许可证为 GPL-3.0-or-later。

## 结论

项目已有可工作的桌面应用、明确的前后端边界、70 项前端测试和 34 项 Rust 测试。当前主要差距是公开协作、干净环境构建、第三方许可和可追溯发布。开源准备阶段不需要重写架构。

本轮把仓库内的基础设施落地到工作区，并绑定本地 `origin`。这不等于源码已经推送、GitHub 设置已经启用或安装包已经公开；这些状态应分别验收。

## 实施顺序

### 第一阶段：可公开阅读与贡献

完成源码/历史与素材来源核对，提交本轮基础文件并首次推送。配置 GitHub About、topics、Actions、默认分支和安全功能。确认 README 链接与 Issue 模板可用，跑通一次远程 CI，再设置所需检查与分支/tag 保护。

维护者负责仓库权限和原创内容确认；提交的配置负责构建规则与协作入口。验收结果是他人可从仓库克隆、按文档运行并提交经过 CI 的 PR。

### 第二阶段：可可靠分发

先完成依赖许可与对应源码汇编，将 notices 纳入各分发包，并在打标签前更新 CHANGELOG 日期，再触发标签构建。对 Release 草稿在干净 Windows 环境验收，在 Release 说明中记录支持环境后公开首个 1.0.0 Release。若已创建标签后发现需要源码修复，使用新补丁版本。

验收结果是公开的源码标签、二进制、许可材料、校验值和发布说明相互对应；用户不用开发环境即可完成安装和一次人工样例校润。

### 第三阶段：持续维护

补截图、故障排查和英文简介；建立依赖 PR 处理节奏。按真实问题补回归、静态检查与性能测试，再决定工作台状态拆分、虚拟列表、签名和自动更新。避免仅为“像开源项目”引入大量框架、目录和徽章。

## 本轮验证与边界

- 整理后 70 项 Vitest、34 项 Rust 测试、前端生产构建、Rust 格式检查和 Clippy 通过。Rust 三个文件仅按 rustfmt 统一格式。本机使用预装的 stable 工具链（rustc 1.96.0）验证；CI 通过 `rust-toolchain.toml` 安装同版本及组件。
- 项目元数据和 `v1.0.0` 标签检查通过，错误版本标签能被拒绝。新增 YAML、Tauri 配置 schema 和维护文档链接检查通过。
- 打包脚本在隔离 Git 仓库中使用明确标注的假二进制验证：7 个附件、源码许可收录、全部 SHA-256、旧输出拒绝及未提交源码拒绝均通过；此项不代表实际安装包已构建或运行验收。
- npm 运行依赖 `npm audit --omit=dev --audit-level=high` 报告 0 个已知漏洞；这不是全部依赖或许可合规结论。
- `git ls-remote` 可以访问目标仓库，未返回分支/tag；本地 origin 已设置。GitHub API 查询遇到未认证速率限制，未核实或修改仓库可见性、保护规则及安全设置。
- CI/Release 文件本地可审查；远程执行、安装器运行验收、完整第三方许可与对应源码汇编仍需按上述阶段完成。
