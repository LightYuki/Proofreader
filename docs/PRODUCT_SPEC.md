# 视觉小说译文校润工具：需求与交互规格

应用版本：1.0.0（固定，未经用户要求不递增）  
更新日期：2026-09-23  
用途：作为后续开发、需求核对及交接的统一参考。

本文记录需求基线及第一版实现决定。工程现已初始化，核心流程已实现；本文中的待定事项和扩展建议不自动纳入第一版。实现与验证状态见第 9 节，使用方式见 [README](../README.md)。

## 1. 产品定位与范围

构建一个轻量桌面工具：导入视觉小说原文 JSON 和对应译文 JSON，结合上下文调用 LLM 检查明显翻译问题，由用户审阅并确认，最终保存校润版 JSON。

已确认的原则：

- 常用场景是中文视觉小说到英文或日文，但程序不限制语言组合，也不提供语言下拉选项；实际语言方向写在风格要求中。
- 使用桌面端；不做在线协作平台或复杂项目管理系统。
- LLM 提供建议，人工决定是否采用。
- 只修改明显有问题或存在明显偏差的译文，避免为了换一种表达而重写。
- 支持手动填写风格要求，以及独立的剧情／人物背景说明。
- 模型服务可自定义 Base URL，API Key 为选填；模型支持获取列表后搜索选择，也可手动填写。
- 已打开文件使用标签切换，最近记录和各文件审阅进度保留到下次工作。
- 保持功能简单，仅保留必要的读取、配对、调用和写回检查。

第一版核心流程：

1. 打开原文与译文 JSON。
2. 填写语言方向、风格要求和可选的背景说明。
3. 按连续片段调用 LLM 检查，显示处理进度，允许停止。
4. 在连续双语正文中审阅建议，接受、保留原译或手动修改后确认。
5. 保存校润版 JSON。

## 2. 输入与输出

### 2.1 JSON 结构与配对

输入为顶层数组，条目包含 `message`，可以同时包含 `name`。

原文示例：

```json
[
  {"message": "窗外下起了雨。"},
  {"name": "小夏", "message": "你今天还要出去吗？"}
]
```

译文示例：

```json
[
  {"message": "It began to rain outside."},
  {"name": "Xia", "message": "Are you still going out today?"}
]
```

配对与保存规则：

- 原文和译文按数组位置一一对应，不依靠文本匹配或 `name` 匹配。
- `name` 作为说话人信息供模型参考。原文与译文中的姓名可以不同。
- 第一版只修改译文的 `message`。
- 输出以导入的译文结构为基础，保留数组顺序、条目数量、`name` 和其他字段；不要求保留 JSON 的原始空白格式。
- 无修改建议、保留原译以及尚未人工确认的条目，继续使用原译文。
- 默认另存为校润版 JSON，之后可以继续更新该校润版文件。

### 2.2 最低必要异常处理

- 文件不能读取或 JSON 不能解析时，明确提示原因。
- 两份数组长度不同、条目缺少可用 `message` 等无法安全配对的情况，提示并停止本次检查，不尝试自动猜测对应关系。
- 缺少 `name` 是正常情况；不将其当作异常或场景边界。
- 模型调用失败与“检查成功、没有发现问题”必须区分。

不引入自动文本对齐、复杂格式修复或完整的控制代码校验系统。

## 3. 校润原则与上下文

### 3.1 检查范围

重点检查：错译、漏译、否定关系错误、人物指代错误、明显语法问题，以及明确违反用户风格要求的表达。

已经成立的表达，即使存在另一种写法，也不主动修改。判断依赖上下文时，修改理由应指出具体依据。信息不足时应保持谨慎，避免把猜测当作确定错误。

人物关系、情节和原意以原文及用户提供的背景说明为依据；译文是待检查对象，不应反过来作为确定剧情事实的依据。

要求模型保留换行、占位符和控制标记，第一版不为此建立复杂校验机制。

语言规则：原文与译文均不绑定语言枚举。遵循风格要求中明确写出的语言方向；没有明确目标语言时保留现有译文的语言，不转成另一种语言。人名、外语词和有意混用的台词不因语言不同而直接判错。修改理由与上下文依据始终使用中文。

系统规则位于 `src-tauri/src/prompts/review.md`，由 `prompts.rs` 组装请求；HTTP 适配与范围检查位于 `llm.rs`。

### 3.2 每次请求携带的信息

- 风格要求：语言方向、语气、表达方式、术语或称谓约定等。
- 剧情／人物背景：人物关系、当前情景等，可为空。
- 本批窗口中的连续原文、译文、说话人和稳定条目索引。
- 明确的本批检查范围；范围外条目只作为上下文。

每批独立携带所需信息，不依赖前一轮聊天历史。第一版不做不断累积的自动剧情摘要。

## 4. 固定滑动窗口规则（已确认）

### 4.1 参数

| 参数 | 固定值 | 含义 |
| --- | ---: | --- |
| 前文 | 15 条 | 只用于理解情景 |
| 检查区 | 最多 30 条 | 本批允许提出修改建议的范围 |
| 后文 | 15 条 | 只用于理解情景 |
| 总窗口 | 最多 60 条 | 前文、检查区和后文的总和 |
| 推进步长 | 30 条 | 处理完整个检查区后移动到下一批 |

一条指一组已配对的原文和译文，而不是分别把原文、译文各算一条。一次请求检查整个检查区，不是对其中每条分别请求一次。

实现中的参数统一来自 `shared/review-policy.json`，由 TypeScript 窗口生成、界面提示及 Rust 请求边界共同读取。它是开发时的固定产品策略，不是新增的用户设置入口。

### 4.2 索引算法

内部统一使用从 0 开始的原始数组索引；界面行号从 1 开始展示。内部区间采用左闭右开约定 `[start, end)`。

```text
N = 配对后的条目总数

for core_start in range(0, N, 30):
    core_end = min(core_start + 30, N)
    context_start = max(core_start - 15, 0)
    context_end = min(core_end + 15, N)

    发送条目 [context_start, context_end)
    只允许检查 [core_start, core_end)
```

例如，文件足够长时，以下均为界面上从 1 开始的行号，端点包含在范围内：

| 批次 | 提供给模型的台词 | 实际检查 |
| --- | --- | --- |
| 第一批 | 1～45 | 1～30 |
| 第二批 | 16～75 | 31～60 |
| 第三批 | 46～105 | 61～90 |

### 4.3 文件边界与剧情边界

- 文件开头缺少前文时自然截断，结尾缺少后文时同样截断。
- 最后一批不足 30 条时，检查剩余条目即可。
- 不为了凑足 60 条而扩大检查区、重复检查条目或跨文件补充上下文。
- 空数组不产生请求；短文件按实际内容处理。
- 各批检查区互不重叠，按序完整覆盖文件。各批上下文重叠是正常行为。
- 不因说话人变化、缺少 `name` 或出现旁白而自动切断上下文。

这里能确定处理的是文件首尾及批次边界。仅凭 `name/message` 无法可靠识别转场、选项分支或路线跳转。实际文件是否按场景划分，以及是否需要手动标记边界，仍待确认。

### 4.4 分批结果的拼接

每条建议必须关联原始数组索引。索引由工具分配，不能随批次重新编号。

1. 只接收属于本批检查区的建议，外围上下文中的修改建议不应用。
2. 以原始索引定位条目，不按模型返回顺序拼接正文。
3. 返回空建议列表表示该批完成且未发现需修改的问题，不表示正文为空。
4. 保留完整译文数组，只在用户确认后替换对应 `message`；不能把模型返回的建议列表直接当作输出文件。
5. 失败只重试对应批次。重试结果更新该批的建议，不重复追加，不影响其他已完成批次。
6. 已人工确认的修改不被重试或新的模型结果静默覆盖。

模型结果使用 `{"issues":[{"index":0,"proposed":"完整替换译文","reason":"中文修改理由","evidence":"可选上下文依据"}]}`。`index` 为原始数组的零基索引，依据中的可读行号从 1 开始。非有效建议格式、截断或空响应按失败处理；空 `issues` 数组表示成功且无建议。

### 4.5 边界验收示例

| 条目数 | 批次数 | 检查区（界面行号） | 最后一批提供的台词 |
| ---: | ---: | --- | --- |
| 0 | 0 | 无 | 无 |
| 1 | 1 | 1 | 1 |
| 29 | 1 | 1～29 | 1～29 |
| 30 | 1 | 1～30 | 1～30 |
| 31 | 2 | 1～30；31 | 16～31 |
| 60 | 2 | 1～30；31～60 | 16～60 |
| 61 | 3 | 1～30；31～60；61 | 46～61 |
| 100 | 4 | 1～30；31～60；61～90；91～100 | 76～100 |

需要验证：检查区无遗漏、无重复；窗口不越界；模型返回乱序时仍能正确定位；失败批次不会被标为无问题；重试不会产生重复建议；输出不会遗漏未修改条目。

## 5. 主工作台交互（已认可）

### 5.1 布局

- 主要区域连续展示原文与当前译文，左右对照，条目对齐。
- 保留说话人和行号，默认使用舒适的阅读间距。
- 右侧显示当前条目的修改差异、可编辑建议译文、修改理由和上下文依据。
- 问题导航可以收起；平时通过上一问题／下一问题定位。
- 点击问题只定位并突出相应台词，不隐藏其他正文。
- 筛选问题只影响问题导航，不将连续剧情正文过滤成孤立的问题句。
- 采用后默认留在当前句，不自动跳转。
- 后台批次切换不导致人工审阅界面强制翻页。
- 工作台使用纯黑、白和中性灰。确认操作和定位边线使用深灰，选中行使用浅灰底；彩色只用于审阅状态灯。修改对照采用灰底、下划线新增、删除线删除。正文不逐行显示“无建议”。文件名和未保存圆点只出现在文件标签中。
- 待审数量、问题列表、正文提示与审阅灯共用同一判断：初次待审以及已采用后再次编辑的草稿都需确认。上一／下一问题只在这些条目中循环；全部处理后禁用跳转，可在问题列表“全部”中回看。

### 5.2 修改与保存状态

应区分条目审阅状态和文件保存状态。

| 类型 | 状态／行为 |
| --- | --- |
| 条目审阅 | 待审、已采用、已保留 |
| 编辑草稿 | 对建议译文进行手动编辑，确认前不改变当前结果 |
| 文件保存 | 有未保存修改、已保存／无未保存修改 |

审阅面板标题的行号旁只显示静态状态灯，不常驻“待审”或保存说明：琥珀色表示待审或已采用后的草稿尚待再次确认，绿色表示已采用，灰色表示保留原译或检查无建议。未检查显示灰色空心灯，检查中为黑色，失败为红色。灯径 12px、交互区域 28×24px，实色不透明；悬停 250ms 或键盘聚焦时显示状态和简短保存说明，Esc 收起说明。提供无障碍名称，不闪烁、不发光。灯色与文字颜色分开设置，状态灯表示审阅决定，不表示文件已保存。

主要操作：

- “采用”：将建议或手动编辑后的内容应用到工作结果；已采用条目再次编辑后，通过“更新修改”重新确认。
- “保留原译”：忽略本条建议，使用原译文。
- “保存”：把已确认的工作结果写入校润版 JSON；首次保存选择新的输出文件。
- 支持撤销／恢复原译，避免一次误操作难以纠正。
- 在条目之间切换时保留手动草稿。
- 采用完成后按钮显示“已采用”并禁用，编辑新草稿后恢复为“更新修改”；保留后显示“已保留原译”并禁用重复操作。底部操作区预留恢复操作的位置，切换审阅状态时主要按钮不跳动。

界面按钮采用短标签；文件格式、保存行为等完整说明留在相关弹窗与使用文档。空工作台提供打开与最近记录入口，正文、问题导航和审阅面板各自承担单一用途。自动保存工作记录与“保存”输出 JSON 是两个独立动作，文件未保存标记仍表示已确认译文尚未写入输出文件。

已实现快捷键：`Ctrl+Enter` 采用修改，`F8`／`Shift+F8` 跳转下一／上一问题，`Ctrl+S` 保存校润版。

## 6. 文件、校润要求与设置的交互优化

本轮范围：保留菜单和聚焦弹窗，简化密钥输入，增加模型获取与选择，以及支持长期工作的文件标签、最近记录和进度恢复。不增加项目管理、模型服务档案或数据库。

### 6.1 文件

使用小型下拉菜单，列出：

- 打开…。
- 最近打开…。
- 保存。
- 另存为…。
- 关闭当前文件。

“打开”进入原文和译文成对选择的窗口。每对文件对应一个标签，重复打开同一文件对会回到原标签。菜单承担命令选择，不承载长期显示的表单。

“最近打开”按最近使用顺序显示文件对与路径，可重新打开；空工作台也显示最近记录。关闭标签保留记录和进度。仅已关闭的记录可“从最近列表隐藏”，保留会话、草稿、人工决定、批次、要求和输出路径，不删除输入或输出 JSON。隐藏状态跨重启保存，并同时作用于最近打开弹窗和空工作台的最近列表；通过“打开…”重新选择同一文件对后恢复进度并重新显示。隐藏写入失败时恢复列表中的记录并报告错误。本轮不增加最近关闭入口。

工作记录自动保存到应用配置目录的 `workspace.json`，包含标签及当前文件、文件路径、建议和草稿、人工决定、批次状态、各文件的校润要求、当前行、输出路径和保存状态。切换文件或关闭程序时，先停止当前检查并写入快照，再切换或退出。重启恢复上次标签和当前文件，运行中的批次转为待处理，不自动调用模型；撤销历史不恢复。

重新打开时检查原文和译文内容是否变化。内容变化则提示重置旧建议、草稿、决定及批次进度，重新载入文件；保持人工选择的校润要求。无法读取文件或工作记录时显示错误，不把失败当作空记录覆盖。工作记录不含 API Key，不自动写入译文 JSON；用户仍通过“保存”输出已确认的改动。

### 6.2 本次校润要求

使用居中弹窗：

- 不提供语言选择控件。风格要求可直接写原文与译文的语言方向，打开时聚焦风格输入框。
- “风格要求”和“剧情背景”分成两个标签页，一次聚焦一类输入。
- 剧情背景默认留空，输入框不显示示例描述。
- 底部提供“取消”和“保存”。
- 保存后的要求用于下一次检查，不自动改写已有建议或已确认译文。

### 6.3 模型设置

使用独立弹窗，纵向排列 Base URL、API Key 和模型，提供“获取模型”“测试连接”“取消”“保存”。API Key 标为选填，本地服务可留空，不提供独立的启用开关。Base URL 和模型名保存在应用配置目录，密钥保存在 Windows 凭据管理器；正在检查时不能修改连接设置与校润要求。

已有密钥时显示“已保存密钥”的占位提示；未编辑且地址同源时继续使用，输入新值可更换，通过“清除”明确移除。更换主机、协议或端口时不复用原密钥，留空按无密钥处理。测试和获取模型不修改设置或凭据，保存才应用更改；配置写入失败时恢复原凭据。旧版禁用的密钥不会因升级重新启用。

“获取模型”使用当前 Base URL 和可选密钥请求 `/models`，无需先填写模型；列表按名称排序、去重，允许输入筛选并选择。服务不提供列表、返回空列表或获取失败时，保留手动填写入口及清晰提示。编辑服务地址或密钥会清除旧列表，迟到响应不覆盖新的表单状态。

已接入 OpenAI 兼容的 Chat Completions 文本接口，非流式请求。Base URL 支持基础地址或完整 `/chat/completions` 地址，模型列表沿用同一接口根路径。测试连接使用当前模型发送简短请求，不承诺自动兼容所有服务商。

### 6.4 聚焦与返回

- 顶栏从“文件”菜单开始，不重复显示“校润”标题。“文件”“校润要求”“设置”共用交互样式，悬停时只改变文字颜色，鼠标操作不留下底框；键盘导航以细下划线标示焦点。
- 打开弹窗时工作台变暗，暂时不可操作，键盘焦点留在弹窗内。
- 表单输入先作为草稿，保存后生效。
- 点击遮罩不会意外关闭弹窗。
- 关闭后返回原入口，保留当前台词、阅读位置和审阅草稿。
- 取消、关闭按钮及 Esc 放弃本次表单草稿；不更改已保存配置。

### 6.5 菜单与 hover 优化（2026-09-24）

保持工作台与弹窗布局、控件尺寸和热区。正文、审阅只读文字、标签与最近记录按所在位置提供右键菜单；输入框保留系统文本菜单。正文“复制当前译文”使用已确认文本或原译文，“编辑本条译文”定位并聚焦现有审阅输入框。标签右键针对被点击的标签，打开菜单不切换文件、不停止检查、不修改审阅决定。

文件菜单、右键菜单共用定位与键盘行为，支持方向键、Home／End、Enter、Esc、菜单键／Shift+F10（适用位置）；菜单限于当前弹窗作用域，外部点击或正文滚动后收起，命令执行前核对目标。模型列表键盘活动项进入可视范围，已选择模型与当前定位项分别表达。

文字与图标操作去除悬停底框，菜单及列表保留直角整行高亮，主要按钮保留明暗反馈，键盘焦点与选中标识继续保留。本轮不补测试，不加入栏宽调整、内容重排或最近关闭；详细约定见 [菜单与悬停交互优化规划](./MENU_OPTIMIZATION_PLAN.md)。

## 8. 第一版实现决定与待定事项

已确定并实现：

- 使用 Tauri 2 + React + TypeScript + Vite，以 Rust 提供文件与网络能力，详见[技术选型与最小架构](./TECH_STACK.md)。
- 风格要求和背景保存在本机偏好设置中，并随各文件进度独立保存；标签、最近记录、建议、草稿和批次进度支持跨次恢复，不持久化撤销历史。兼容旧版含语言选项的记录，只忽略废弃字段，不重置进度。工作记录格式版本仍为数字 1，与应用版本独立。
- 重新检查使用原导入译文，保留已经采用、保留原译和手动编辑过的审阅项，不静默覆盖人工决定。
- 批次串行处理；停止会取消当前请求并忽略迟到结果，继续时处理剩余批次。失败不自动重试，由用户操作“重试失败批次”。
- 单批超时、接口拒绝、输出截断及无效建议格式显示为失败。固定 60／30，不自动拆分超长文本。
- 校润版以同目录临时文件写入后替换，不允许覆盖本次导入的原文或译文；已有校润输出可继续更新。

仍待实际使用确认：

1. 输入是否常包含多个场景或剧情分支，是否需要手动分段入口。
2. 超长文本是否需要额外的简单拆分方式，以及超大文件是否需要虚拟列表。
3. 菜单与弹窗方案的使用体验、Windows 最低支持版本及其他平台支持。

这些细节应按轻量工具的定位处理，避免扩大第一版范围。
